摘要

系统是一套面向东华大学松江校区 253 间多媒体教室的垂直运维平台，采用 Flask + SQLite + 原生 JS 单页前端，PyInstaller 打包为 Windows 一键安装包。v1.5.4 在 v1.5.3 排课查询的基础上，补齐了教室筛选、可用/使用过/使用率统计、三时段可视分组与考试类型，并将通用授权、构建门禁和安装器复制纳入发布流程；同时通过自定义 PyInstaller hook 将服务端从 89.1MB 压到约 45.9MB。

本版的核心工程判断有三条：排课数据与业务 state 分离，避免把每天新增的位图数据塞进单行 JSON；导入用事务整日替换，保证“要么完整一天、要么完全不动”；统计口径写进接口与页面文案，让“可用 156 / 使用过 135 / 使用率 86.5%”这类数字能被解释，而不是靠口头约定。

02系统定位与总体架构

系统不是通用的 ITSM，也不是纯前端工具。它的边界很明确：一台 Windows 机器（或局域网内一台服务器）承载 Flask 服务与 SQLite 数据，用户通过浏览器访问；安装包负责把运行环境、服务、快捷方式和开机启动一起交付。

2.1 总体架构

浏览器（PC / 手机）原生 JS 单页应用；hash 路由；按需加载 xlsx/jspdf；localStorage 仅存 token 与少量偏好
桌面启动器Edge/Chrome --app 窗口；服务未启动时先拉起 server.exe

2.2 技术栈与取舍

层选型取舍理由
后端Python 3.11 + Flask 3.1团队熟悉、依赖少、打包成熟；单机/局域网规模足够。生产环境仍用 Flask 内置服务器，是已知待改项。
数据库SQLite零运维、单文件、随安装包交付；写并发低。全量 JSON + 宽表的组合适合“读多写少、报表复杂”的场景。
前端原生 JS（IIFE）无 Node 构建链，现场可直接改、直接发；代价是模块化和类型检查缺失。
PDF 解析PyMuPDF文本型 PDF 可按坐标稳定取词，不依赖 OCR；打包体积通过 hook 控制。
打包PyInstaller onefile + Inno 风格自绘安装器客户现场只需一个 exe；服务端、启动器、安装器分三个产物，便于回滚。

2.3 部署形态

单机模式（默认）

server 仅监听 127.0.0.1，安装在同一台值班电脑；桌面快捷方式直接打开本机页面。适合值班室单机使用。

局域网模式

安装时勾选“允许局域网访问”，写 access.txt=lan，监听 0.0.0.0；防火墙仅放行专用网络 + 本地子网，其他电脑用服务器 IP 访问。

旧部署升级时，若目标目录已有数据库且没有 access.txt，安装器默认保持 0.0.0.0，避免升级后局域网用户失联；全新安装默认仅本机。

3.2 关键实现亮点

01

保存事务同成同败

D1 修复把 state JSON 与三张 mart 表放进同一事务；mart_sync 不再自行 commit。失败返回 500 并回滚，前端保留快照、指数退避重试，避免“界面显示成功、数据其实没写”。

02

权限从菜单走到接口

报表 6 个 JSON、CSV、审计上报全部加权限校验；/api/state 按发生变化的顶层域校验，越权 403 且不写库。权限点不再只是“隐藏菜单”。

03

排课数据独立建模

不写入 state，单独两张表 + 位图；导入整日事务、原 PDF 留档、sha256 可追溯。避免每天新增的 160 行数据放大全量 JSON 的读写成本。

04

可验证的交付工程

47 项排课测试、13 项通用授权测试、55 项权限回归、95 项 UI 冒烟；打包后对 exe 做 health/preview/授权冒烟，不只验证源码。

04排课查询实现详解

排课模块是本版最重的功能。它的难点不在页面，而在“把一张人看的 PDF 表，稳定地变成机器可查询的位图”，并把统计口径固定下来。

4.1 范围与约束

  • 只覆盖《东华大学松江校区值班记录表》中实际存在的一教、二教：每个 PDF 160 行，其中 156 间普通教室（松1xxx / 松2xxx）+ 4 个特殊行（1号学院楼同传室、待定、松1254(不使用)、松江体育馆电化）。
  • 只解析占用状态「课 / 借 / 考」；不解析课程名、教师、借用人。四教、化工楼、中南楼、机房暂无数据。
  • 每天一个 PDF（可多页），不做自动抓取；同日重复导入默认拒绝，显式覆盖才替换。
  • 数据与业务 state 分离：不写入 /api/state，避免全量 JSON 放大。

4.2 解析流程

读取PyMuPDF 打开
→
定日期页脚年月日
→
定列表头 1–13 + 时间词
→
定行x0<95 取教室
→
落格课/借/考按最近行列
→
合并多页按教室名
  1. 日期与星期：从页脚“2026 年 11 月 01 日”提取日期；优先用“星期一”文字，缺失时按日期推算。同一天多页按教室名合并。
  2. 列定位：表头数字 1–13 的词与 08:15/09:00 等时间词共同确定 13 列；时段从时间文字动态读取，不写死。缺列时按等距兜底，避免某页表头轻微偏移导致整页失败。
  3. 行识别：教室名在左侧列（x0 < 95）；首行可能紧贴表头（y≈87），因此阈值取 y < 80，并用 cy <= 80 标记；这一改动修正了 11-02 从 157 间到 160 间、课节 671→675。
  4. 占用落格：对「课」「借」「考」「考试」四个词，取最近的行与列；同一格出现多个类型时，优先级 class > exam > borrow，保证冲突可解释。
  5. 容量与过滤：容量取右侧数字列（x>500）；只保留 松[12]\d{3} 与四个特殊行；容量为 0 且无任何标记的版式标题（如“体育馆”）丢弃。
  6. 输出：{date, weekday, slots, rooms, page_count, source_sha256, summary}；解析失败抛 ScheduleParseError，逐文件展示原因。
解析器的脆弱点

坐标阈值对版式变化敏感：换字体、换打印缩放、表头增删列都可能导致行列错位。当前用“表头数字 + 时间词 + 等距兜底”降低风险，但换版式仍应先用样例回归，再上线。

4.3 数据模型

CREATE TABLE schedule_days( date TEXT PRIMARY KEY, weekday TEXT, slots_json TEXT, source_name TEXT, source_sha256 TEXT, imported_at TEXT, imported_by TEXT, room_count INTEGER, regular_rooms INTEGER, class_count INTEGER, borrow_count INTEGER, exam_count INTEGER ); CREATE TABLE schedule_rooms( date TEXT, name TEXT, building TEXT, digits TEXT, capacity INTEGER, special INTEGER, class_mask INTEGER, borrow_mask INTEGER, exam_mask INTEGER, PRIMARY KEY(date, name) ); CREATE INDEX idx_sr_date ON schedule_rooms(date);

位图设计：第 i 位对应第 i 节（0–12），1 表示占用。前端按连续位合并 colspan；统计节数用 bit_count，时长 = 节数 × 45 分钟。位图比“每节一行”更紧凑，160 间 × 13 节只需 160 行/天。

迁移：老库启动时幂等建表；regular_rooms、exam_count、exam_mask 通过 PRAGMA table_info 检查后 ALTER TABLE 补齐，并回填 regular_rooms。

原始 PDF：保存到 <DB目录>/schedules/<date>.pdf；覆盖导入时同日期文件替换；source_sha256 记录内容哈希，便于判断“同一天是否真的是同一份表”。

4.4 接口契约

方法与路径权限行为
POST /api/schedule/previewsettings多文件 PDF/ZIP 解析预览；逐文件返回 date/summary/exists/error，不写库。
POST /api/schedule/importsettingsfiles + replace=1；同日默认 409，覆盖需显式确认；事务内整日删插。
GET /api/schedule/days?from&to登录月历数据（最多 400 天）；每天附课/借/考分钟；summary 含 available_rooms/used_rooms。
GET /api/schedule/day?date=登录单日 slots/rooms/summary/source；未导入 404 + not_imported。
DELETE /api/schedule/day?date=settings删除当日数据与原始 PDF。
GET /api/schedule/source?date=登录下载原始 PDF（send_file）。

导入事务：先校验全部文件解析成功与冲突策略，再在单连接事务中 DELETE schedule_rooms/schedule_days → INSERT → 落盘 PDF → COMMIT；任一步失败整体回滚。审计写“数据 / 导入排课表”，详情含日期、教室数、课/借/考节数。

限制：单文件 20MB、总量 80MB、最多 40 个 PDF；ZIP 内仅取 PDF；文件名不参与业务判断，日期以 PDF 内容为准。

使用总时长(课 + 借 + 考) × 45 分钟；只统计普通教室200,655 分钟
为什么“使用过”不是“可用”

“可用教室”是容量口径（156 间），“使用过”是去重口径（135 间），两者必然满足“使用过 ≤ 可用”。11 月只导入了 10 天，剩余 21 间在这 10 天内没有占用，所以没有被计入。页面用“本月使用过”而不是“使用教室”，并在帮助文案里写明公式。

4.6 前端实现

  • 月历：原生 <input type="month"> + 「今天」；周一开头 42 格；只有已导入日期高亮并显示课/借/考计数；切换月份时若今天不在本月，自动选第一个有数据日。
  • 月卡：8 项统计（有考试时动态追加考节/考试时长），2 列布局；使用率单独一卡；已导入天数显示在右上角。
  • 日视图：顶部 8 个统计卡；工具栏为“全部/一教/二教/其他 + 只看有占用”；表格两行表头（上午/下午/晚上分组），单元格按连续同类型 colspan 合并，但不跨时段合并；三组不同底色 + 竖向分隔线。
  • 教室筛选：roomNeedle() 去空格/小写，一教/1教→松1、二教/2教→松2；roomMatch() 同时匹配名称与数字编号；输入值放在 st.roomQuery，切换日期/月份/今天都保留，只有「清除」或重新进入视图才重置。
  • 抽屉：点击单元格显示日期、时段、时长、类型、容量；连续时段显示“08:15–11:35 / 3 小时（4 节）”。
  • 上传：多选 PDF/ZIP → 预览卡（新日期/已存在/解析失败）→ 冲突勾选覆盖或二次确认 → 导入后刷新月历并选中首个导入日。

5.1 通用授权（内部机制）

环节实现
签发build_release.ps1 读取仓根 release_license.json（org/edition/max_users），以构建日 +1 年调用 tools/make_license.py --machine "*" --expires ... --users ...，输出 build/license/license.json。
校验license_key.load_status() 对 machine="*" 跳过本机机器码比对；RSA 签名、到期、时间回拨校验不变。
安装installer_gui.install()：数据目录已有 license.json 时不覆盖；没有才复制随包通用授权；完成页显示单位/版本/用户数/到期日。
打包版试用allow_trial = not sys.frozen（可用 DHU_OPS_ALLOW_TRIAL=1 覆盖）；打包版缺少授权时返回 invalid，不静默生成 30 天试用。
用户上限max_users=20：创建账号、重新启用账号时统计 users WHERE active=1，达到上限返回 403。
到期7 天只读宽限后锁屏；客户凭机器码签发正式授权覆盖。
残余风险

通用授权文件可被复制到多台机器，但到期日固定，不能换机续期；如果未来要求“完全防多机”，需要联网激活或服务端授权，离线模式做不到。当前把它定位为“交付便利 + 到期约束”，不是强防破解。

5.2 教室筛选（方案 A）

日视图顶部统计保持全楼全局，输入框右侧单独显示当前教室小计。这样既能看到“今天整体用了多少”，也能回答“这间教室今天什么时段有课”，两个问题不互相污染。筛选状态放在视图层，切换日期/月份保留，避免每换一天都要重新输入。

5.3 PyMuPDF 瘦身

PyMuPDF 2.1 安装体积约 104.5MB；官方 PyInstaller hook 对 pymupdf >= 2.0 执行 collect_data_files('pymupdf')，把整个包收进产物，其中 layout/resources/onnx/ 约 50MB（版面/表格 AI 模型，本系统未使用）、mupdf-devel/ 约 6.5MB、__pycache__ 约 5MB；真正必需的是 mupdfcpp64.dll（25.2MB）+ _mupdf.pyd（12.4MB）。

06关键机制与数据契约

这一章是“改代码前必须知道”的部分：state 怎么读写、冲突怎么处理、权限在哪里校验、审计由谁写。

6.1 业务 state 与乐观锁

  • 单行 JSON：state 表保存 settings / tickets / patrols / assets；GET 全量返回，POST 全量提交。
  • rev：每次保存 rev+1；客户端携带 baseRev，不一致返回 409 并附最新 state；前端合并 tickets/patrols 后重试。
  • 权限域：denied_state_fields() 按发生变化的顶层域检查权限；管理员恒放行；首次写入（空库）放行；未改动字段原样提交不受影响。
  • mart：保存成功后 mart_sync() 全量重写三张宽表，与 state 同事务；失败整体回滚并返回 500。
  • 已知边界：409 合并只覆盖 tickets/patrols，settings/assets/kb 的本地改动在冲突时被远端覆盖；目前靠单账号单会话 + 低并发缓解。

6.2 鉴权、权限与审计

机制实现
登录PBKDF2-HMAC-SHA256（20 万次）+ salt；旧 SHA-256 登录时自动升级；单账号只保留最新会话。
会话sessions 表存 token，24 小时过期；改密/重置/停用会删除对应用户会话。
权限点12 个菜单权限；require_perm(*keys) 任一满足；管理员恒放行。
报表/CSV/审计6 个报表 JSON 需 reports；CSV 需 data/tickets/reports 之一；审计按类别校验，页面类全员、登录/用户/系统仅管理员。
审计audit_write() 写 audit_logs；客户端上报为“尽力而为”，关键动作由服务端写。

6.3 备份与恢复

备份走 sqlite3 backup API，最多保留 20 份；恢复读取整个上传文件、校验 SQLite magic 与 state/users 表、os.replace(tmp, DB) 热替换后 init_db()。已知边界：无上传大小限制、恢复时不清 sessions、热替换期间有并发风险；建议在维护窗口执行。

9.3 验收标准（建议）

  • 自动导入：目录出现 PDF 后 1 分钟内可查；失败在页面有红色提示；重复文件按 hash 跳过。
  • 性能：253 间教室 × 1 年数据下，保存 P95 < 1.5s，月历 P95 < 800ms，日报表 P95 < 2s。
  • 权限：仅 dashboard 权限的账号无法通过任何接口读取工单明细；越权返回 403 且审计留痕。
  • 可靠性：连续 100 次导入/覆盖无脏数据；任意失败后 state 与 mart 一致。
  • 可运维：安装包在干净 Windows 10/11 上完成安装、启动、卸载；升级不覆盖已有授权与数据。

9.4 取舍原则

先保“每天能用”，再谈“架构漂亮”

排课模块的下一阶段优先解决漏传、查不到、口径不清这三类现场问题；state 拆分、前端工程化、可观测性属于“数据量或团队规模上来后再做”的事。任何改造都应保留灰度开关与回滚路径，避免为了架构目标牺牲值班连续性。

mart报表宽表，由 state 全量同步。
位图13 位整数表示 13 节占用，第 i 位对应第 i 节。
可用教室单日普通教室总数（当前 156）。
使用率本月使用过（去重）÷ 可用教室。
